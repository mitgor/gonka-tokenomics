Tier 2 -- Community Plugin (Near-term, v1.4 candidate):
- Description: npm package (openclaw-plugin-gonka) auto-configuring Gonka as provider with agent-native extensions exposed as MCP tools

- Risk: Medium -- must match OpenClaw's plugin API which may evolve

Tier 3 -- Built-In Provider (Medium-term goal):
- Description: Gonka added to OpenClaw's ~20 built-in providers -- users configure with just API key, no baseUrl/models config needed

- Effort estimate: 1-2 weeks engineering (PR preparation) + unknown review time
- Timeline: Target 3-6 months after Tier 2; depends on community traction and maintainer relationship
- Success criteria: PR merged into openclaw/openclaw main; Gonka appears in `openclaw models list` output
- Risk: High -- requires OpenClaw maintainer approval; "community approach, not cold PR" per CONTEXT.md decisions

Tier 4 -- Preferred Partner (Long-term aspiration):
- Description: Co-development relationship with OpenClaw team -- Gonka-specific optimizations, joint features, marketing collaboration
- Prerequisites: All Tier 3 items, significant user base on Gonka via OpenClaw (1000+ active developers), demonstrated commitment to OpenClaw ecosystem (multiple merged PRs, active community presence, skill contributions)
- Deliverables: Joint roadmap for agent-native features, co-branded developer content, Gonka-optimized agent templates in OpenClaw defaults
- Effort estimate: Ongoing relationship investment
- Timeline: 6-12 months after built-in provider status
- Success criteria: Joint announcement or feature; Gonka mentioned in OpenClaw official communications
- Risk: Very high -- depends entirely on relationship quality and Gonka's traction

**Section 4: Built-In Provider PR Strategy**

Document the community-first approach to getting Gonka merged as a built-in provider (per CONTEXT.md decision: "community approach, not cold PR -- build relationship first"):

4a. Community Relationship Building (Pre-PR Phase):
- Month 1-2: Establish presence in OpenClaw Discord (#help, #models, #users-helping-users). Answer provider configuration questions. Share Gonka config snippets when relevant (not spammy -- only when users ask about cost-effective providers or agent-native features)
- Month 2-3: Contribute non-Gonka PRs to openclaw/openclaw (bug fixes, documentation improvements, test coverage). Build contributor credibility. Target 3-5 merged PRs before proposing Gonka provider
- Month 3-4: Engage with OpenClaw maintainers on GitHub Discussions about provider architecture. Understand their priorities, pain points, and decision-making process for adding new built-in providers
- Throughout: Track and document community adoption metrics (users mentioning Gonka in Discord, config snippets shared, issues filed about Gonka integration)

4b. PR Preparation (Technical):
- Study existing built-in provider implementations in openclaw/openclaw source (examine how OpenRouter, Together AI, Groq providers are structured)
- Implement Gonka provider module matching OpenClaw's code patterns exactly (TypeScript, same file structure, same config schema)
- Write comprehensive tests matching OpenClaw's test patterns (jest, same assertion style)
- Write documentation page matching existing provider docs format
- Include model catalog with accurate pricing, context windows, and capability flags (reasoning, toolUse, vision)
- Handle Gonka-specific headers (X-Gonka-Session-ID, X-Gonka-Tier) as optional provider extensions that enhance but don't break standard flow

4c. PR Submission Strategy:
- Open a GitHub Discussion BEFORE the PR: "RFC: Add Gonka as Built-In Provider" with rationale (unique features: sessions, memory, tiering), adoption metrics, and link to existing community plugin
- Wait for maintainer feedback and address concerns
- Submit PR only after positive signal from at least one maintainer
- PR description template: include why Gonka is different from existing providers (not just another OpenAI wrapper -- agent-native extensions), community adoption data, link to npm plugin download stats

4d. Handling Rejection:
- If rejected for insufficient adoption: Set concrete metric targets, revisit in 3 months
- If rejected for technical reasons: Address feedback, resubmit
- If rejected for ecosystem reasons (too many providers): Propose as "community-maintained" provider with lighter integration

4e. Realistic Timeline:
- Pre-PR community building: 2-4 months
- PR preparation: 1-2 weeks
- Review and iteration: 2-4 weeks (depends on maintainer responsiveness)
- Total: 3-6 months from starting community engagement
- Note: This is NOT a guaranteed outcome -- it depends on Gonka's traction and OpenClaw team's priorities
